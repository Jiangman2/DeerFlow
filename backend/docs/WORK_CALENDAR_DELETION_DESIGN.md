# 日程删除设计（本轮不启用）

2026-11-02 用户确认：本轮只设计删除，先不启用。代码的执行 Action、Work HTTP适配和批量白名单仍不提供删除；OAuth拥有宽泛更新权限不等于平台开放全部操作。

## 之前保留关闭的原因

此前用户明确选择先完善读取和编辑。删除还需要核对“取消当前请求”和“取消已创建日程”的区别、目标是否唯一、日程归属、参会人、周期系列以及执行结果不确定时的处理。预览和本人确认是必要条件，后端校验与回执也不能省略。

## 后续可评审的首期范围

- 默认关闭，由运维选择环境后显式启用；先在本地UAT验证，生产另行决定。
- 仅本人主日历、本人组织、无其他参会人/会议室的非周期、有明确起止时间的单条日程。
- 周期系列、例外实例、全天日程、共享日历、他人组织和带参会人的日程保持阻止；不把退出会议替换为删除会议。
- 首期一次明确选择一条。用户说“取消明天的日程”时，先完整查询并展示实际候选；有多条则补问，不能默认第一条或悄悄删除全部。

## 执行协议

1. 从当前可信Work消息和现有绑定取得本人身份；不接受模型选择owner、token、任意API或未经核对的资源ID。
2. 获取当前用户授权，完整查询候选，读取目标实时信息和参与人，核对首期范围。
3. 形成独立删除预览，写明标题、具体日期时间、操作对象及删除影响；确认绑定完整快照、任务版本、本人身份和有效期。
4. 本人确认后再次读取并比较快照、归属、参与人和周期状态；目标变化就使预览失效，要求重新核对。
5. 在共享PostgreSQL短事务内认领一次执行，之后才调用固定的Work删除适配器。换题、绑定变更、旧确认重放不能开始新的删除。
6. 保存服务端执行回执并核验目标状态。鉴权失败、权限不足和网络错误不能当作“已删除”；请求超时则记录结果未知，先核查，不自动重试。

实际Work接口若不支持条件删除，最后一次读取与删除之间仍存在竞态；评审和UAT需明确这一限制，不能把本地快照比较称作提供方事务。不能承诺自动恢复已经删除的日程。

## 权限与存储

预期沿用现有日历读取/更新权限，但具体接口语义和实际部署的Work权限目录仍需在启用前核对；本轮不新增OAuth scope或要求ITC开新权限。未来状态、预览和回执仍可使用现有加密JSON记录与版本屏障，无需先新增数据库表。

## 启用前的验收

覆盖模糊目标、同名多条、误把停止任务当删除、非本人组织、其他参会人/会议室、周期/全天、过期或被修改的预览、换题后确认、跨用户确认、重复确认、多Pod同时认领、权限失败及提交后断网。验证真实Work状态及回执，不能仅凭模型回复“成功”。

本设计不构成删除功能的启用，也不授权自动清理此前测试产生的日程。
