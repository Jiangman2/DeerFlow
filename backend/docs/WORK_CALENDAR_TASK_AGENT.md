## 理解与补问

入口模型只判断普通任务、Work文档或日历以及新任务/续接。日历进入受限领域代理，通过本地工具提交字段补丁、检查草稿、补问和完成提案。工具没有HTTP、授权或写入能力。

草稿独立保存操作、目标条件、标题/变更、单次或有限多次、日期集合/连续天数、每天开始时间和每次时长。仅显式字段改变，未提及字段保留，明确null才清空。每天三小时连续三天由服务器展开三条，不以首日开始/末日结束替代。

入口的“新任务/续接”判断只是提示，不能直接丢弃同一领域正在补问的草稿。同类新任务通过独立本地工具说明重建原因，并引用本条用户输入；服务端保存重建依据。若只是出现不同标题而任务关系不清，先确认是修改原安排还是另建。明确从创建转为查询时清除不兼容的新建条件；从查询选择“第二条”编辑时保留经核对的候选线索，执行前仍重新读取目标。

创建和纠错在完成提案前必须通过当前完整草稿的本地校验，核对精确条数和每条时间；完整时直接形成非执行提议，不再为额外的finish声明请求一次模型。授权、真实目标核对、预览及本人写入确认仍由后续服务完成。

单条超过24小时的创建先确认连续跨日或逐日独立；跨日确认是服务端状态，不是模型补丁可直接设置的布尔值。仅上轮服务端明确补问后，模型可通过受限工具或结构化span_choice表达本条用户选择，并引用当前原文。相同时间或安排方式的重述保留确认，实际时间、数量或安排方式变化才撤销。选择每日独立时保留已知日期，未明确的每天钟点和时长继续补问，不把原跨日总时长复制给每天。

仍缺信息时只问缺失字段。重复补问会展示已保留的业务条件；模型未完成结构校验或超过总时限时给出明确重试引导，不转普通模型编造平台未接入。

日历领域最多6次模型工具调用，最多2次格式修复；完整提议通常只需分类加一次领域理解。错误反馈只含已知字段路径及固定错误类别，不含模型原始值。排队预算独立默认10秒（1～30），模型执行总预算默认90秒（5～180）；显式旧值30仍有效。服务仅另设1秒watchdog约束未遵守超时的注入planner，不追加重试。首次失败明确当前输入尚未保存；已有草稿时只声明保留此前验证条件。日志用消息哈希关联排队、模型开始、完成和失败及耗时。

写提案还要通过服务端日期来源校验。只补“每天9点、持续3小时”不能使开始日期自动变成今天；“未来三天”单独出现只提供条数，仍需明确起点。校验只使用原始用户文本、同任务已核对的绝对日期和已选对象的受限事实，排除助手问题、文档正文和模型自报的依据。相对日期按消息接收时间解析，缺少时间戳的历史文本不能按今天重解释。无法唯一核对的表达会补问明确日期，其他条件保留；查询路径不受这个写入日期校验影响。

日期依据仍放既有加密任务上下文，明确另起任务不会继承。参数来源校验不能替代对所有否定、指代和业务含义的理解，逐项预览与本人确认仍是必需步骤。

## 已开放的有限能力

- 读取个人主日历，沿用既有最多31天的完整查询边界。
- 新建单条日程，或在明确日期上按相同钟点、相同时长新建最多10条独立日程。
- 查询并选定一条本人组织、无其他参会人的非周期日程进行既有受限编辑。
- 显式纠正之前的结果时，使用本人成功回执或已查询候选作定位线索；重新读取实时日程后提出修改。可将一条错误跨日安排缩短为首日，再新增剩余日期，仍需完整确认。

不同日期各自不同钟点/时长、任意跨领域多步骤写入及真正周期规则不属于本轮有限批量能力。需要补问或拆分请求，不能丢掉不支持的条件。删除保持关闭，见 [删除设计](WORK_CALENDAR_DELETION_DESIGN.md)。

## 预览与执行

后台完整读取所涉现有日程，展示时间重叠，不擅自挪动原定时间。批次预览列出条数、每条起止和时长；编辑同时展示修改前后值。确认绑定协议版本、完整动作、快照与预览。任何改变都需要新确认。

共享状态先认领父计划，再在每项开始前核验当前任务并认领该子项。模型和HTTP调用不占数据库锁；已开始的操作保留回执。后台识别换题并更新任务版本后，尚未认领的项会停止；识别完成前或已经认领的操作可能继续，已完成项不会自动撤销。

后续消息会从本人持久执行记录判断当前任务是否已开始，而非依赖模型或上一进程保存的“完成”提示。同一任务补问即使更换代次，也不能直接把已执行的新建草稿再次提交；“改成10点”应定位已创建对象后编辑。确实另外新建时，需要本轮本地重建工具的校验证明，再创建新的任务编号。执行中、部分成功、结果未知或有界历史无法完整核对时，先核查原结果，不盲目复制整批。

新SQL任务在现有conversation JSON里维护执行索引，父计划认领与“已开始”索引在同一短事务内写入；继续任务保留索引，明确新任务重置。这样不以用户全部历史记录的扫描上限判断新任务是否执行过。旧版无索引任务继续保守核对，不伪造“未执行”。模型等待期间若有旧确认抢先执行，任务代次更新后再次查询执行状态，阻止复用新建草稿。

Work不提供整个批次的跨请求事务。部分成功、失败/结果未知和未执行分别报告；不自动重新提交整个批次。接口幂等标识与持久执行记录用于防重复，不作为未知结果可盲目重试的依据。不同用户的SQL确认不共用进程级全局执行锁，同一主体仍由共享执行租约保护。

## 升级和回退

沿用现有环境与权限配置。本轮不启用删除、不扩大OAuth请求、不改管理员保存凭证的优先级。

更新前暂停Work新任务并等待已确认写入结束。所有Gateway必须使用兼容的新协议后再恢复；旧Pod不理解批次/草稿状态，不能混跑保证。协议2拒绝旧版未完成授权任务和待确认预览，用户重新发起；有效grant、绑定与已完成回执保留。

回退前同样暂停并结束新任务，保留回执、表和密钥。旧镜像不应直接续跑新批次。生产70 Pod容量和真实UAT业务验收需要分别验证；隔离测试不会证明这些已经完成。
