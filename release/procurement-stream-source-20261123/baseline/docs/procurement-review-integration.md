# 技术委托要求审核：两端接口约定

当前只实现场景二。对方提交后，我们以配置的账号及数字员工创建独立任务，完成审查并自动生成 Word，随后回传；不等待用户确认。

## 对方调用我们的提交接口

`POST /api/v1/integrations/procurement-review`

请求头：`Authorization: Bearer <双方约定的提交密钥>`。
请求格式：`multipart/form-data`，只有以下两个字段。

| 字段 | 类型 | 用途 |
|---|---|---|
| `request_id` | 字符串 | 对方生成的本次审查唯一编号，用来对应业务记录并防止网络重传重复审查 |
| `files` | 多个文件 | 本次技术委托要求、立项论证意见、立项审批页、预算下达通知等材料 |

`request_id` 长度 1–128，字母或数字开头，可包含字母、数字、下划线、点、冒号、短横线。不需要再传业务单号、账号、数字员工名、场景、回调地址、提示词或模型密钥。对方自行保存此编号与其业务单的对应关系。项目材料可合并在同一 PDF 中；不要混入其他项目材料。

支持 PDF、DOC、DOCX、PNG、JPG、JPEG。最多 12 份，单份 30 MiB，总计 100 MiB；重复文件名拒绝。边缘网关的上传限制也需要与此协调。附件先全部接收、校验并落盘，再创建持久化任务。接收请求期限 120 秒；文件解析在后台执行。

返回 HTTP 202：

```json
{"request_id":"SCM-2026-001-review-1","job_id":"系统生成的UUID","status":"queued"}
```

`job_id` 是我们内部任务的对应号，供双方排查。相同 `request_id`、文件名和内容重传，返回原任务，不重新调用数字员工；重传可调整文件顺序。相同编号但材料不同返回 409；修改材料重新审查时必须使用新的 `request_id`。

错误：401 凭据不正确；404 未启用；408 上传超时；413 超限；415 类型不支持；422 参数、空文件或重复文件名错误；503 工作服务不可用。畸形 multipart 由解析器返回 400。

```bash
curl --fail-with-body "$DEERFLOW_URL/api/v1/integrations/procurement-review" \
  -H "Authorization: Bearer $PROCUREMENT_SUBMIT_KEY" \
  -F 'request_id=SCM-2026-001-review-1' \
  -F 'files=@技术委托要求.docx' \
  -F 'files=@立项论证意见.pdf' \
  -F 'files=@立项审批页.pdf' \
  -F 'files=@预算下达通知.pdf'
```

密钥只保存在双方后台，不放到对方网页或文档里。

## 我们调用对方的报告接收接口

对方开发一个 `POST` 接口，HTTPS 地址及独立的回传密钥部署时配置在我们服务端。我们发送 `Authorization: Bearer <回传密钥>` 和 multipart：

| 字段 | 用途 |
|---|---|
| `request_id` | 原样回传对方的审查编号 |
| `job_id` | 我们的任务号 |
| `status` | `succeeded` 或 `failed`，表示任务执行结果，不是审查是否符合 |
| `message` | 完成提示或不含内部敏感信息的失败说明 |
| `report` | 成功时的 Word 文件；失败时不传 |

对方先持久化结果与文件，再返回 HTTP 200 或 204；按 `job_id` 去重，重复接收返回成功，不创建重复报告。回传可能因确认响应丢失而重复。我们最多尝试 10 次，间隔从 30 秒逐步增加到 1 小时；回传失败只重传已保存的同一报告，不重新审查。重试耗尽保留报告与 `delivery_failed` 记录，需运维处理。

第一期没有新增查询、下载、取消接口。调用方收到提交返回后显示处理中，回传后显示结果；回传长时间未到，携带 `request_id` / `job_id` 联系管理员。提交返回丢失可原样重传。

## 本次审查规则

版本：`technical-requirements-20261117-v5`，共八项。八项规则、固定风险基准、提示话术及逐项材料对应关系由任务提示词直接下发，不需要上传审查矩阵或单独的审核要点文件。数字员工配置可使用 [完整岗位提示词](procurement-review-agent-prompt.md)。

| 序号 | 审查内容 |
|---|---|
| 1 | 未修改信息残留：全文及上下文，区分正式内容与空白样表。 |
| 2 | 内容明确性：服务/供货、合同后期限、成果/规格清单、标准封面、验收及中期检查；与立项论证意见比对指标。 |
| 3 | 知识产权：不允许强制论文第一作者或发明人排序归属总院人员；专利权人归属可约定。 |
| 4 | 四个签署位置：只检查编制、审查、审核、批准是否有人名或签名，不判断人员职务、权限或签名真实性。 |
| 5 | 倒签风险：服务开始日期对比立项审批页提供的审批完成日期；不以水印或文件修改日期替代。 |
| 6 | 签约主体：以预算下达通知文件头的组织全名为准，不取“财务管理部文件”或收文单位。 |
| 7 | 前后数据：统一单位和口径后比对金额、数量、期限等。 |
| 8 | 模板：选择适用的一个技术要求模板，核对必要结构与内容，不混合套用全部模板。 |

缺材料、未完整读取、签名/文件头看不清，报告写“无法判断”；不强行生成通过结论。自动报告分为基本信息、核心审查结果、补充意见与材料覆盖、审查结论。每项保留材料位置、证据、依据及建议。

未修改信息残留、知识产权、倒签、签约主体为高风险基准；内容明确性、签署位置、数据一致性、模板符合性为中风险基准。只有“不符合”才计入对应风险命中；“符合”为未命中，“无法判断”为待核实。数字员工生成 Word 前自查八项及材料覆盖，按固定规则填写风险及结论，核心结果使用八列表格：序号、检查项、判定状态、风险等级、命中内容及材料位置、基准依据、修正建议、提示。风险字段不增加对方提交接口参数。

## 服务端配置与文件部署

功能默认关闭。生产启用前需要配置：

```text
PROCUREMENT_REVIEW_ENABLED=true
PROCUREMENT_REVIEW_OWNER_USER_ID=<既有有效账号ID>
PROCUREMENT_REVIEW_ASSISTANT_ID=procurement-review
PROCUREMENT_REVIEW_REFERENCE_ROOT=/opt/deerflow/procurement-references/v1
PROCUREMENT_REVIEW_SUBMIT_KEY=<提交专用密钥>
PROCUREMENT_REVIEW_CALLBACK_URL=https://partner.example/api/review-result
PROCUREMENT_REVIEW_CALLBACK_KEY=<回传专用密钥>
```

必须先通过既有数字员工管理功能建立对应自定义 Agent；`ASSISTANT_ID` 是该账号下已保存的实际 Agent 标识，支持平台允许的中文、字母、数字和连字符，最长 64 字符。显示名可能与实际标识相同，也可能不同，不能仅凭显示名推导。配置必须同时绑定该员工的 `OWNER_USER_ID`；不得匹配到另一个账号下名称相似的员工。应配置阅读全文、表格与原始页图能力；无需给 Agent 回传密钥或允许其自行调用对方接口。建议专用 Agent 不启用与采购审查无关的外部业务工具。提示词与八项规则由服务端注入。

参考目录以**只读卷**挂载给 Gateway。五组参考资料为：制度 `policy`、四个模板 `template_research` / `template_testing` / `template_software` / `template_equipment`。不挂载审查矩阵或 `review_points` 文件。每组必须含原件及核对过的完整 UTF-8 文本伴随文件，保留表格、章节和页码定位；不使用检索返回的片段代替全文。签名与封面仍需核对原件图像。

目录中的 `manifest.json` 指定版本、角色、相对文件路径及 SHA256：

```json
{
  "version": "scenario2-references-v1",
  "documents": [
    {
      "role": "policy",
      "original": {"path": "policy/original.doc", "sha256": "实际64位SHA256"},
      "text": {"path": "policy/fulltext.md", "sha256": "实际64位SHA256"}
    }
  ]
}
```

示例只展示一组，实际必须列齐五组。完整参考包合计上限 128 MiB，文本须由资料维护人员确认没有截断或缺页。内部制度、模板、项目材料与密钥均不提交 Git。

每个任务从只读挂载目录读取该版本资料，并复制到该账号的独立任务 uploads 中，通过**现有线程数据卷**供 Sandbox 读取。Sandbox 不需要直接看见 Gateway 的 `/opt` 路径，也不需要另改 Provisioner 挂载。系统核对参考清单及原件哈希；报告验收时再次核对输入未被修改。保留经过上传安全校验的项目原件（PDF 安全净化可能移除主动行为），不会用解析文本替换原件。企业解析器可用时流式处理文件并生成全文 Markdown，解析失败写入报告说明，由 Agent 读取原件或明确无法判断。

多实例 Gateway 使用 PostgreSQL、共享 RWX 线程数据卷及共享参考版本；内存数据库不支持此接口。SQLite 仅适用单机。所有实例必须采用相同账号、Agent、回传地址及规则版本。参数变更后不应直接改旧任务归属；配置不一致的旧任务进入 `configuration_blocked`，由运维核对。

队列采用 SQL 租约与心跳，最多 4 个采购任务处于准备/启动/运行状态（与其他类型任务预算独立）。启动意图先落库；启动后崩溃按持久化 Run 元数据恢复，不自动重新提交不确定的模型任务。30 分钟任务期限包含排队、解析和执行；超时请求取消并回传失败，但远端 Run 所属进程的取消确认可能滞后，不能将此视为模型提供方硬超时。Word 保存在线程目录内的私有交付快照，不作为未经 `present_files` 验收的聊天附件发布。

## 直接交付 Word（v5）

数字员工完成八项审查，先检查内容齐全，再直接生成并重新读取 DOCX 核对，调用现有 `present_files` 完成 Office 预览与发布。接口不再接收结果 JSON，也不重新生成 Word。只接受原成功 Run 的单一 DOCX 成果，核对文件大小、包结构、四部分、八行检查、状态风险一致性及结论，再保存字节完全相同的私有交付快照用于回调重试。

接口的 DOCX 检查只证明结构齐全及表内逻辑一致，不能替代数字员工全文审查，也不能证明材料识别、引用、签名或事实正确。缺材料判为无法判断的责任在数字员工审查与生成前自查；真实材料需业务验收。保留输入哈希和原 Run 绑定。接口参数不变。

Word 中的证据采用文字说明：文件名、页码或章节/表格位置、原文摘录及问题描述，不插入截图或原件页面图片。审查签名与预算通知文件头时仍需查看原件，核查结果用文字描述；无法辨认则写无法判断。问题高亮指报告中文字的高亮，不需要截图能力。
