MinerU asynchronous migration: capacity inventory r1 (2026-10-14)

PURPOSE
Determine why the last sample had 9 desired / 6 ready Worker replicas, collect
Dispatcher real health/capacity, inspect WeKnora queue configuration, and estimate
the CPU/RAM request budget for a possible 64-worker target.

RUN
Upload the checksum-verified archive to /home/cnooc on datax-01. Copy it into a
new root-private /run control directory, verify the trusted archive SHA256,
extract there, verify PACKAGE.SHA256 and run bash ./run-datax01-capacity.sh as root.
No credentials are requested. Python 3.7+ and kubectl are required. The script
uses /etc/kubernetes/admin.conf and namespace deer-flow. No package installation.

SCOPE
Only Kubernetes GETs, owned ready baseline Adapter/Dispatcher Pod execs for
source hashes and loopback /health, and new local evidence/download files.
No Secret API reads, provider requests, document submission, image import,
scaling, Pod replacement, configuration change, database write or rollout.
The existing Dispatcher /health may perform its ordinary Worker health probes
and refresh expired quarantine state. It does not submit parse work.

The four inspected Deployments are deer-flow-mineru-adapter,
deer-flow-mineru-dispatcher, weknora-app and weknora-docreader. Pod event messages
are categorized, not printed. Only allowlisted env settings/health fields appear.
Other namespaces' bound Pod resource requests are counted in memory, not printed.
Credential values, raw process args, Pod logs and provider responses are omitted.

OUTPUT / DURATION
Progress is printed before each Deployment, Pod health and node inventory.
Individual kubectl calls have bounded timeouts. An elapsed-time check stops the
next phase after 15 minutes; an already running call may take its remaining
bounded timeout. Failure is not automatically retried.
The protected report is /var/lib/mineru-capacity-<random>/RESULT.json (root/0600).
The wrapper prints a new /home/cnooc/mineru-capacity-download-<random> directory
owned by cnooc, containing capacity.log and, on success, RESULT.json.
Return those two files, or the diagnostic log on failure. Do not export Secrets.

INTERPRETATION
inventory=COMPLETE means collection finished, NOT acceptance of 64 concurrency.
ready_for_rollout always remains false. A changed baseline or missing health
receipt must be reviewed; the tool never silently approves or modifies it.
Steady-state slots are request-based upper bounds with current owned workers
replaced, not 64 additional workers. They include ordinary/init/sidecar resource
requests, node readiness, pressure, required node affinity and hard taints.
They do not prove actual CPU/RAM peaks, disk space, architecture eligibility,
all inter-Pod affinity/topology rules, rollout surge, Redis backlog, queue
performance, provider capacity or interactive latency under load.
The 64 target is a test/review ceiling, not a promise of greater throughput.
