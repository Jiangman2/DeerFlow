下面进入小节：22.1 先用一句人话理解 DeerFlow。

DeerFlow 的本质可以先用一句话表示：

> DeerFlow 接收一个带有身份和上下文的任务，把任务放进一个可恢复的有状态 Agent 图中；图不断调用模型和工具，工具不断更新状态，运行时不断保存状态并把过程广播给前端，直到得到最终答案或触发安全终止条件。

这句话中每个动词都对应一个真实机制：

表格口述：人话，底层机制；接收任务，Gateway 解析 HTTP 请求；带有身份，user、thread、assistant、run context；放进 Agent 图，Lead Agent factory + LangGraph；调用模型，LangChain chat model；调用工具，ToolNode/Agent middleware/tool router；更新状态，State reducer + Command(update=...)；保存状态，Checkpoint、Run record、Store、event log；广播过程，StreamBridge + SSE；可恢复，checkpoint + resume command；安全终止，权限、循环、token、递归、取消和错误 Middleware。

这里的第一个重要底层原则是：

> 前端发送的是“运行意图”，Gateway 负责把它变成“受信任的运行上下文”；Agent 不应该直接相信浏览器传来的每一个字段。

例如浏览器可以请求某个模型，但 Gateway 仍然需要检查模型是否存在、用户是否有权使用它、请求的递归上限是否超过服务器上限、非交互字段是否被外部调用者伪造。

下面进入小节：为什么先创建 RunRecord？。

因为运行可能立刻失败，也可能浏览器马上断开。如果等模型成功后才创建记录，系统就无法回答：

这次请求是否真的启动过？ - 谁发起的？ - 使用了哪个模型？ - 为什么没有结果？ - 是否曾经处于 running？

RunRecord 是一次执行的“出生证明”。它不等于最终答案，也不等于 checkpoint。

下面进入小节：22.4 Gateway 如何把“用户输入”变成 LangGraph 输入。

普通消息和恢复命令是两种不同的入口：

代码示例口述：这里的代码用于说明数据结构或调用顺序，重点不是逐字朗读代码，而是理解它如何把输入传给下一层，并接收处理结果。

普通消息表示：从当前 ThreadState 继续处理一条新的用户输入。

Command(resume=...) 表示：图此前已经停在某个 interrupt 或人机交互点，现在把用户的结构化回答交给原来的图继续运行。

这两个入口不能混淆。若把人机交互回答重新包装成普通用户消息，模型可能把它理解成一个新问题，而不是原工具调用的恢复数据。

运行配置并不是一个地方一次性生成的，而是逐层合并：

图示口述：这张图展示了客户端可提交字段、允许字段过滤、服务器默认值与限制、认证用户/Thread/渠道、知识库与权限范围、trusted runtime config、Lead Agent factory之间的关系。整体方向是从输入开始，经过处理和执行，再回到状态、事件或最终输出。

可信配置通常包含：

thread_id：当前 Thread。 - user_id：服务端确认的用户身份。 - model_name：最终解析后的模型。 - thinking_enabled：最终有效思考模式。 - agent_name：当前自定义 Agent。 - subagent_enabled：是否开放子 Agent。 - non_interactive：是否来自受信任的调度路径。 - channel_name：web、GitHub、IM 或 scheduler。 - weknora_knowledge_base_ids：知识库范围。 - recursion_limit：经过服务端裁剪的图预算。

关键点是：客户端传入的字段是“请求”，服务端合成后的字段才是“事实”。

下面进入小节：22.6 run_agent 是如何把多个系统接到一起的。

run_agent 可以看成一座桥。它一端连接 HTTP/Run 管理，一端连接 LangGraph Agent，中间接入持久化和事件：

图示口述：这张图展示了RunRecord、run_agent、trusted config、graph_input、agent_factory、Compiled Agent Graph、Checkpointer、Store、StreamBridge、Run Event Store之间的关系。

它至少要同时解决五件事：

Agent 运行时能拿到正确的 Thread 和用户上下文。 2. Agent 的状态能从正确的 checkpoint 恢复。 3. 图事件能被序列化为前端理解的事件。 4. 后台执行和浏览器 HTTP 连接可以解耦。 5. 无论成功、失败、取消还是异常，都执行必要的 finally 清理。

因此 run_agent 往往比“调用 graph.ainvoke”复杂得多。它承担的是 DeerFlow 运行时语义，而不是 LangGraph 最小示例里的单次函数调用。

下面进入小节：22.11 为什么工具错误要被转成 ToolMessage。

如果工具直接抛出异常并结束整个 Run，模型没有机会：

修改参数重试。 - 换另一个工具。 - 解释为什么不能完成。 - 请求用户补充信息。

但不是所有错误都应该交给模型。例如权限越界、平台保密违规、Sandbox 隔离冲突和硬预算超限，可能必须直接终止。

下面进入小节：22.12 ThreadState 的“状态账本”思维。

不要把 ThreadState 理解为“当前页面的 JSON”。它更像 Agent 的账本：每个字段有自己的所有者、写入时机和合并规则。

表格口述：字段，主要写入者，主要消费者，为什么需要 reducer；messages，模型、工具、用户输入，模型和前端，对齐消息序列与追加语义；sandbox，Sandbox Middleware/工具，Sandbox 工具，防止同一 Thread 出现两个隔离环境；thread_data，ThreadData Middleware，文件工具，建立 workspace/uploads/outputs 关系；artifacts，present_file/结果 Middleware，前端 Artifact 面板，追加且去重；todos，Todo 工具/Middleware，前端 Todo，新列表覆盖旧列表；goal，Goal API/运行时，prompt 和前端，普通更新不能意外清除；delegations，Subagent executor，Lead Agent 和前端，并行事件合并不能倒退；viewed_images，ViewImage Middleware，视觉模型，保存引用而不是大块二进制。

一个很实用的调试问题是：

> 这个字段是谁写的？写入是完整替换、追加、合并、清空还是幂等更新？

DeerFlow 同时存在三种“时间”：

图示口述：这张图展示了模型产生事件、实时事件时间，前端马上看到、图状态时间，checkpoint 保存、应用持久化时间，Run/Thread/usage 提交之间的关系。整体方向是从输入开始，经过处理和执行，再回到状态、事件或最终输出。

它们不一定完全同时发生。比如前端可能已经看到“正在生成标题”，但标题更新要等 Run finally 才写入 Thread metadata；停止按钮可能已经让前端显示 idle，但数据库中的终态提交稍晚完成。

这就是前端需要“立即失效缓存 + 后续 refetch”的根本原因：实时体验和最终一致性是两条不同的时间线。
