本集标题：扩展 DeerFlow 的正确方式。

欢迎收听 DeerFlow 源码与运行机制导读。

下面进入小节：20.1 新增工具。

建议步骤：

在 Harness 内实现工具，不直接依赖 app.*。 2. 明确输入 schema、返回值和 State update。 3. 添加超时、错误、取消和 secret 处理。 4. 放入配置工具组或内置工具集合。 5. 检查工具名称、同步/异步调用和重复注册。 6. 增加单元测试和一次 Agent 运行测试。

下面进入小节：20.2 新增 Middleware。

先回答三个问题：

它需要在模型前、工具前、工具后还是运行后执行？ - 它要修改 messages、tools、state 还是 runtime context？ - 它如何在重试、恢复、取消和并行场景保持幂等？

下面进入小节：20.3 新增 Skill。

Skill 应提供：

清晰的触发条件。 - 可执行的步骤。 - 失败处理和验证方法。 - 需要的工具清单。 - 安全限制。 - 示例输入输出。

不要在 Skill 中写平台 secret、数据库密码、Kubernetes credential 或“忽略系统规则”的指令。

下面进入小节：20.4 新增 Gateway 路由。

Gateway 路由需要同时考虑：

认证。 - Thread/用户授权。 - CSRF。 - 输入校验。 - 响应脱敏。 - 异步阻塞 IO。 - 管理员跨用户读取边界。 - 与 Nginx 路由优先级的关系。

下面进入小节：20.5 新增企业集成。

建议把外部系统放在 Gateway adapter 或明确的 Harness provider 后面，避免把外部 API 细节散落到 Agent、前端和 Skill 中。凭据、代理、CA、重试、审计和错误映射应集中管理。

下面进入小节：20.6 文档与测试同步。

当前仓库明确要求代码变更同步更新 README 和相关 AGENTS.md。功能变更至少应更新：

用户如何使用。 - 开发者应该从哪里进入源码。 - 配置字段和部署影响。 - 安全边界。 - 测试命令和回归用例。

本集小结：请记住，本章的概念最终都要回到 DeerFlow 的运行链路中，观察它们如何影响状态、工具、事件和最终输出。
