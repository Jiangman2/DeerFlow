下面进入小节：22.16 Sandbox 的深层逻辑：不是“执行命令”，而是“受控副作用”。

模型的文本推理没有直接修改外部世界；工具执行才会产生副作用。文件写入、命令、网络请求、模型外部 API 都可能改变系统或泄露数据。因此 Sandbox 需要控制：

图示口述：这张图展示了模型请求执行命令、确认 Thread/Sandbox 身份、确认路径在允许根目录、准备允许的环境变量、命令/扩展/网络策略、执行、限制输出并脱敏、事件/审计/State之间的关系。整体方向是从输入开始，经过处理和执行，再回到状态、事件或最终输出。

因此，Sandbox 工具的正确设计不是把 subprocess.run(command) 包一层，而是把执行看成一个有身份、有目录、有环境、有超时、有审计的受控操作。

下面进入小节：22.17 Local Sandbox 与 Kubernetes Sandbox 的共同抽象。

两者的执行介质不同，但上层需要的契约相同：

表格口述：契约，Local，Kubernetes/AIO；Thread 隔离，本地根目录，Pod/远程 workspace；命令执行，本地进程，HTTP exec API；文件读写，本地文件系统，sandbox 文件 API/挂载卷；环境变量，进程环境/结构化注入，请求级环境/Secret；回收，本地目录清理，Pod idle timeout/delete；安全边界，路径与命令检查，网络、Pod、Token、Secret、路径。

这就是 Sandbox 抽象的价值：Agent 不必知道它运行在哪一台机器上。

下面进入小节：22.19 Skill 与 MCP 的底层组合关系。

用“说明书”和“遥控器”来理解：

Skill 是说明书：告诉模型某类任务应该怎么做。 - MCP 是遥控器：给模型一个连接外部系统的按钮。

一个 Skill 可以建议使用一个 MCP 工具，但两者生命周期不同：Skill 是模型上下文内容，MCP 是工具运行时能力。工具策略必须在两者交汇处生效：不能因为 Skill 写了“请调用某工具”，就绕过工具权限。

下面进入小节：22.20 Memory 与 summary 的底层区别。

摘要回答：

> 为了让当前 Thread 继续运行，旧上下文怎样压缩？

长期记忆回答：

> 未来其他 Thread 是否需要保留这条关于用户或任务的事实？

摘要是当前执行优化，通常进入 ThreadState；长期记忆是跨 Thread 数据，通常进入 Store 或 Memory backend。把二者混为一谈会导致：

每次摘要都污染长期记忆。 - 长期记忆无法按用户/namespace 管理。 - 用户删除一个会话时误删全部长期偏好。

下面进入小节：22.25 恢复一次运行时，底层真正检查什么。

恢复不是“点击继续”这么简单，至少要检查：

Thread 是否仍存在且属于当前用户。 2. checkpoint 是否属于这个 Thread。 3. 目标 Run 是否仍可恢复。 4. interrupt 的身份是否匹配。 5. resume payload 是否符合 schema。 6. 原 Sandbox 是否仍然可用。 7. 旧的上传文件和输出文件是否仍存在。 8. 当前工具目录是否与 checkpoint 的 catalog hash 相容。 9. 当前模型和 Agent 配置是否允许继续。 10. 恢复是否会与另一个正在执行的 Run 冲突。

任何一项失败都可能需要“安全地重新开始”或提示用户，而不是盲目重放。

四种终态对前端和审计的意义不同：

Success：任务完成。 - Error：任务失败，需要看错误原因。 - Cancelled：任务被主动终止，不应伪装成普通错误。 - Interrupted：任务还没有终态，它正在等待恢复。

最核心的循环只有一句话：

> 模型根据当前 State 决定下一步；工具根据模型决定产生副作用并返回结果；运行时把结果合并回 State、保存 checkpoint、发布事件；模型再根据更新后的 State 决定下一步。

DeerFlow 的大量代码，都是在让这个循环变得可配置、可恢复、可观察、可安全执行、可面向真实文件和真实企业系统。
