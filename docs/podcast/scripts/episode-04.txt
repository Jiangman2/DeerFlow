下面进入小节：0.37.4 幂等性和副作用。

如果模型因网络重试再次调用工具，结果会怎样？

查询工具通常天然幂等。 - 创建订单、发送邮件、删除文件不是天然幂等。 - 生成报告可以使用固定 Artifact 名称或 Run ID 去重。 - 状态更新可以使用事件 ID 去重。

下面进入小节：0.38 Skill 理论：可发现、可加载的任务知识包。

下面进入小节：0.38.1 Skill 是什么。

Skill 不是单纯的提示词，也不是一个普通 Tool。它更像一个可加载的任务知识包：

代码示例口述：这里的代码用于说明数据结构或调用顺序，重点不是逐字朗读代码，而是理解它如何把输入传给下一层，并接收处理结果。

下面进入小节：0.38.2 Skill、Tool、Prompt 的边界。

表格口述：概念，解决的问题，是否直接产生副作用；Prompt，当前一次调用如何表达要求，通常不直接产生；Skill，某类任务长期可复用的知识和流程，通过工具间接产生；Tool，执行一个明确动作，经常会产生；Agent，根据目标动态选择动作，通过 Tool 产生。

下面进入小节：0.38.4 Skill 的风险。

Skill 的文字会影响模型行为，因此可能包含：

过度授予工具权限的建议。 - 诱导泄露 secret 的指令。 - 与系统策略冲突的“忽略前面规则”。 - 不安全的命令。 - 过时的文件路径或部署假设。

Skill review、allowed-tools、沙箱和平台保密 Middleware 共同构成防线。

下面进入小节：0.39 Agent、Tool、Skill、Harness 的组合关系。

图示口述：这张图展示了用户目标、Harness 提供运行环境、Agent 负责动态决策、Skill 提供方法论/流程、Memory 提供历史背景、Tool 提供动作能力、Sandbox 隔离外部副作用、MCP/外部服务、更新 State、权限、预算、事件、恢复之间的关系。整体方向是从输入开始，经过处理和执行，再回到状态、事件或最终输出。

用一个具体问题区分它们：

> “请分析 Excel 并生成 PPT”

LLM：生成“我需要先读取文件”的语言或 tool_call。 - Agent：决定先读 Excel，再分析，再生成 PPT。 - Skill：告诉它怎样设计报告、怎样验证 PPT。 - Tool：真正读取 Excel、运行 Python、生成 PPT。 - Sandbox：隔离这些命令和文件操作。 - Harness：控制整个过程的状态、事件、恢复、权限和预算。

下面进入小节：0.40 Middleware 理论：横切关注点的统一插槽。

下面进入小节：0.40.1 什么是横切关注点。

日志、权限、错误处理、重试、计时、预算和 tracing 会影响很多业务动作，却不应该被复制到每个 Tool 和每个 Agent 节点里。这类功能叫横切关注点。

下面进入小节：0.40.2 Middleware 和装饰器的区别。

装饰器通常包住一个函数；Agent Middleware 可以感知更丰富的生命周期：

一次 Agent 开始前。 - 模型调用前后。 - 某个工具调用前后。 - 每个 State 更新后。 - 整个 Run 结束时。

下面进入小节：0.40.3 为什么 Middleware 顺序会改变语义。

如果先做摘要再做 token 计算，token 统计可能只统计压缩后的上下文；如果先做权限过滤再做工具 schema，模型看不到被禁止工具；如果先执行工具再做错误转换，异常可能直接打穿图。

下面进入小节：0.42 规划理论：计划、执行、反思和终止。

复杂 Agent 通常包含四种认知动作：

规划：把目标拆成步骤。 2. 执行：调用工具完成步骤。 3. 观察：读取工具结果。 4. 反思：判断是否需要修正方案。

图示口述：这张图展示了目标、计划/分解、执行工具、观察结果、评估是否达到目标、调整计划、结束之间的关系。整体方向是从输入开始，经过处理和执行，再回到状态、事件或最终输出。

Todo Middleware 不是“好看的清单”，它可以让计划显式存在于 State 中，帮助模型和前端共享进度；但 Todo 本身不是事实证明，最终仍需工具结果和验证步骤。

LLM 输出具有概率性，不能把它当作普通业务函数。因此可靠 Agent 必须形成“概率内核 + 确定外壳”：

确定性外壳包括：

参数 schema。 - 工具 allowlist。 - 用户和 Thread 授权。 - 路径和命令检查。 - token budget。 - recursion limit。 - loop detection。 - checkpoint 和 event seq。 - 终态规则。

下面进入小节：0.44 Super Agent 理论：为什么 DeerFlow 不只是一个 Agent。

Super Agent 通常意味着：一个 Lead Agent 可以协调多个专用 Agent、工具、知识库和执行环境。

图示口述：这张图展示了Lead Agent，理解目标、规划、综合、研究 Subagent、代码/Bash Subagent、数据分析 Subagent、知识库检索 Agent、结果摘要、统一答案/Artifact之间的关系。整体方向是从输入开始，经过处理和执行，再回到状态、事件或最终输出。

Super Agent 的难点不是“多调用几个模型”，而是：

怎样分配任务。 - 怎样限制并发和递归。 - 怎样传递上下文而不爆炸。 - 怎样合并子任务结果。 - 怎样处理一个子任务失败而其他任务成功。 - 怎样让前端显示每个子任务。 - 怎样避免子 Agent 无限创建孙 Agent。
