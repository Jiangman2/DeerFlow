下面进入小节：0.34 Harness 理论：为什么需要一个 Harness。

下面进入小节：0.34.1 Harness 是什么。

Harness 这个词原意是“马具”或“安全带”。在软件系统中，它表示一层负责把能力接起来、约束起来、观察起来的运行框架。

对大模型系统而言，Harness 通常负责：

创建和配置模型。 - 组织消息和上下文。 - 注册工具。 - 维护 Agent State。 - 执行模型—工具循环。 - 管理 Middleware。 - 保存 checkpoint 和长期数据。 - 发布事件。 - 处理取消、恢复、重试和错误。 - 施加权限、预算和安全策略。

因此 Harness 不等于“调用模型的 SDK”：

图示口述：这张图展示了Model SDK，只解决如何调用某个模型、LLM API、Harness，解决如何让模型可靠地完成任务、Tools、State、Policy、Runtime、Persistence之间的关系。整体方向是从输入开始，经过处理和执行，再回到状态、事件或最终输出。

下面进入小节：0.34.2 SDK、Framework、Harness、Application 的区别。

表格口述：层，主要问题，DeerFlow 中的对应物；SDK，如何调用一个服务，模型 provider SDK、数据库 client；Framework，如何按统一方式组织某类程序，LangChain、LangGraph；Harness，如何把多个能力组成可控的运行系统，deerflow-harness；Application，具体产品怎样给用户使用，Gateway、Frontend、Channels、WeKnora 页面。

LangGraph 可以提供图执行机制，但它不知道 DeerFlow 的上传目录、平台用户、企业审计、Skill policy、外部 Agent launch 或具体前端消息协议。Harness 正是把通用框架和具体可靠运行要求连接起来的地方。

下面进入小节：0.34.4 Harness 的四个边界。

一个成熟 Harness 通常有四条边界：

能力边界：模型能调用哪些工具。 2. 状态边界：哪些数据属于当前 Thread，哪些属于长期 Store。 3. 执行边界：代码和文件在哪个 Sandbox 中运行。 4. 信任边界：哪些字段来自可信服务器，哪些只是客户端请求。

DeerFlow 的 Harness/App 分层，就是把“可复用 Agent 执行能力”和“某个产品的 HTTP、用户、企业集成”分开。

下面进入小节：0.35.2 Transformer 的直觉。

现代 LLM 大多建立在 Transformer 结构之上。无需先掌握全部矩阵运算，可以先理解三件事：

Tokenizer：把文本切成模型能处理的 token。 - Embedding：把 token 映射成向量。 - Attention：让当前位置关注上下文中与它相关的其他位置。

图示口述：这张图展示了文本、Tokenizer、Token vectors、Self-attention，决定关注哪些上下文、多层 Transformer、下一个 token 的分数、采样/选择、输出 token之间的关系。整体方向是从输入开始，经过处理和执行，再回到状态、事件或最终输出。

Attention 让模型能够把“这个文件”与更早的 sales.xlsx 联系起来，把“它”与前文的地区汇总联系起来。但这仍然是上下文内的模式计算，不是传统数据库查询。

下面进入小节：0.35.3 Logits、采样和 temperature。

模型最后会给每个候选 token 一个分数，称为 logits。运行时可以：

直接选概率最高的 token。 - 按概率随机采样。 - 使用 temperature 调整概率分布的尖锐程度。 - 使用 top-k/top-p 限制候选范围。

temperature 较低通常更稳定，较高通常更多样，但不会让模型自动获得事实或工具权限。
