# v2.1.0 批次 17：交付回执的存储前置

## 范围与边界

- #4365 `1c7531242cabe5593788843d7212f01dbff1a22f` 的 `RunEventStore.put_if_absent`：Memory、JSONL、DB 均以 `(thread_id, run_id, event_type)` 去重，返回首次记录与 created 标记，重复重试不占用新 seq。不改变普通 put/put_batch 的 append-only 行为。
- #4938 `c88c2975c91538ba0ae5d5dfc1061ab01bf26a3f`：JSONL 同一线程批量写入多个 run 时，各自写入对应文件；同一线程的某个文件写失败，尝试恢复本批已触碰文件的原始字节长度。不是跨文件崩溃原子事务，也不是跨线程事务，恢复失败仍明确记录错误。
- 以正式 v2.1.0 代码核对，保留已在企业树中的 #5439 取消后等待 I/O 收敛、#5455 JSONL 锁代际、#5462 DB 锁代际和 Unicode 分隔符修复。新 singleton 同样使用 `_run_mutation`，不重新引入取消后磁盘线程脱离锁的问题。
- DB 使用普通 writer 的 PostgreSQL advisory transaction lock；两个独立 store 实例共享去重/seq 互斥。SQLite 仍只有单实例 async 锁保证，不宣称多进程安全。Memory/JSONL 同样不作为生产多 worker 后端。
- 企业附加保护：已有 receipt 带不同 owner 时，带用户上下文的重复写拒绝返回该记录，不生成第二份；可信无用户上下文的恢复可保留首次 owner。此内部写接口不能替代上游的 thread/run 授权。
