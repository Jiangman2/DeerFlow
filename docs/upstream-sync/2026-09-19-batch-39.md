## Behavior

- Concurrent inbound messages for the same channel conversation continue to
  share one thread-creation lock generation while a creator or queued waiter
  still participates.
- If the first creator fails or is cancelled, a caller that arrived later
  cannot bypass an already queued creator and create a duplicate DeerFlow
  thread.
- Cancelled waiters release their participation without leaking idle lock
  entries.
- A shared lock table remains safe when tests or embedding hosts use it from
  separate asyncio event loops running in different threads.

## Enterprise adaptation

The upstream waiter-aware async lock helper is introduced only at the existing
enterprise channel thread-creation boundary. The current channel identity,
authentication, topic binding, metadata backfill, and thread persistence paths
remain unchanged.

Upstream's thread-side keyed lock and its separate goal/checkpoint worker
refactor are intentionally not included in this batch. They are not required
to close the channel race and would enlarge the regression surface beyond this
single concurrency boundary.
