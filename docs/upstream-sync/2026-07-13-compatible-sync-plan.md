# DeerFlow 官方更新兼容式同步方案

本文档定义企业版 `main` 与 DeerFlow 官方 `upstream/main` 的同步方式。目标是：在保留企业历史定制和现有用户行为的前提下，逐步吸收官方新能力。

## 当前基线

- 企业主干：`main`，当前基线提交 `9f093c5b3`
- 企业部署分支：`codex/k8s-single-node-deploy`，与 `main` 保持一致
- 官方旧基线：`7a6c4a994`
- 官方最新基线：`37580862b`
- 官方增量范围：`7a6c4a994..37580862b`
- 官方增量规模：新增 350 个文件，修改 402 个文件，删除 1 个文件

## 总原则

1. 企业 `main` 是事实基线，所有历史定制默认保留。
2. 官方更新不能默认改变现有用户可感知行为。
3. 既有文件允许修改，但只能做加法式兼容扩展。
4. 新功能如果对现有逻辑零影响，可以直接增加。
5. 新功能如果会改变入口、后台行为、权限边界、数据库结构或部署默认值，必须通过 feature flag 或独立 PR 接入。
6. 每个同步 PR 必须通过保护审计脚本和本地验证。

## 什么可以直接合入

- 官方新增文档。
- 官方新增测试、评审、说明材料。
- 未被现有入口 import 的独立模块。
- 新增类型、新增函数、新增翻译键，且旧类型、旧函数、旧翻译键语义不变。
- 新增脚本，且不会自动改变现有构建、部署、启动流程。

## 什么必须 feature flag 或独立 PR

- 新页面、新导航入口、新菜单项。
- 新后台服务、新 scheduler、新 worker、新 webhook。
- 新 API 路由挂载。
- 数据库迁移或持久化模型语义变化。
- 聊天主流程、上传流程、线程搜索、权限认证、登录跳转、部署参数变化。
- 会影响 WeKnora、数据湖 SSO、智能体广场代理、企业看板、企业外观的任何修改。

## PR 列车

建议按以下顺序同步，避免一个巨型 PR 混入隐性行为变化。

1. **同步护栏 PR**
   - 添加本方案文档。
   - 添加保护路径清单。
   - 添加审计脚本。
   - 跟踪第三方技能包。

2. **非侵入新增 PR**
   - 合入官方纯新增且未接入主流程的文件。
   - 不修改企业既有入口。

3. **后端兼容层 PR**
   - 新增 API 或服务前先保持未挂载或 feature flag 关闭。
   - 旧 API 行为不变。

4. **前端兼容层 PR**
   - 新增 i18n key、类型字段、hook、工具函数。
   - 保持旧页面、旧组件和旧默认行为不变。

5. **功能启用 PR**
   - 每个官方新功能单独启用。
   - 测试服务器先开，生产服务器后开。

## 强制审计

每个同步 PR 至少执行：

```bash
python scripts/verify_enterprise_preservation.py --base main
cd frontend && pnpm check
cd backend && .venv/Scripts/python.exe -m pytest tests/test_auth.py tests/test_auth_middleware.py -q
```

审计脚本会检查：

- 相对企业 `main` 不删除任何已有文件。
- 保护路径没有变化。
- 修改既有文件必须在允许清单中登记。
- 新增文件可以存在，但需要人工确认是否会自动接入现有行为。
