# v2.1.0 批次 09：PostgreSQL 连接回收与查询超时

## 来源与实现

- 固定目标 `v2.1.0` / `345f08be00c8a9495079b732a39b46aa9af1584e`。
- 适配官方 #4230 / `39493406105d58e91a584002fb475c6147f26245`，并核对正式标签最终实现。
- `database.pool_recycle` 默认 300 秒、必须大于零；`database.command_timeout` 默认 30 秒、必须大于零，显式 null 关闭命令超时。
- 统一构造 ORM asyncpg engine 参数，与上一批 schema/search_path 合并，首次连接及自动创建数据库后的重试使用同一参数。
- 保留企业员工同步存储、psycopg checkpoint/Store 的独立边界；这不是所有数据库客户端或 Agent turn 的统一超时。
- 示例配置及 Helm 嵌入配置版本推进到 33，记录默认值和重启边界；没有修改本机私有配置或生产配置，没有新增数据库迁移。

## 验证

- 先引入上游定向测试，出现缺失 helper/配置字段的 3 个预期失败，再实现。
- 配置、engine 重试及真实 PostgreSQL 定向回归 **44 通过**（9.06 秒）。
- 真实 PostgreSQL 断言慢查询在约定期限失败、rollback 后连接可用、schema 保持；限定单连接池，先证明立即取回同一连接，再证明超过回收期限更换 backend PID，排除池内连接轮换造成假阳性；显式 null 允许超过短测试期限的查询完成。
- 加强回收断言后，最终联合回归 **1292 通过、5 warnings、无跳过**（171.91 秒）。范围包括 schema、checkpoint、配置重载、持久化/迁移、员工 SQL、调度、运行准入/取消/恢复、后台 trace 和渠道。不是全仓库回归。
- 示例 YAML 和 Helm 内嵌 YAML 解析及值检查通过；未把它宣称为 Helm 渲染/集群验收。
- 使用批次 08 的 loopback/tmpfs 临时 PostgreSQL，未连接生产。
