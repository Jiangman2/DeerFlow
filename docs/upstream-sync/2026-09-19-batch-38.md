# Upstream Sync Batch 38 — Cancellation-Safe JSONL Mutations

## Scope

- Enterprise branch start: `93df06388`
- Recovery tag: `enterprise-pre-upstream-batch38-20260919`
- Official behavior adapted from `6c697f306`.

## Behavior

- Once a JSONL event-store mutation acquires its per-thread lock, caller
  cancellation waits for the admitted filesystem operation and bookkeeping to
  settle before `CancelledError` is propagated.
- Repeated cancellation cannot release the lock early and let a delete
  overtake an older write, or let an older delete erase a later acknowledged
  write.
- A caller cancelled while it is still waiting for the lock starts no disk
  mutation.
- A multi-thread batch drains only its current thread group after cancellation;
  later thread groups do not start.
- If an admitted operation fails after cancellation, cancellation remains the
  primary result and the settled operation failure is retained as its cause.

## Enterprise adaptation

The enterprise JSONL store does not yet contain upstream's later
`put_if_absent` and multi-run atomic batch architecture. This batch applies the
cancellation boundary to the mutation surfaces that actually exist here:
single writes, per-thread batches, thread deletion, and run deletion. It builds
on Batch 37's weak lock-generation registry without changing current JSONL
file layout or sequence semantics.

Production uses the PostgreSQL database event store, so this improves local and
lightweight single-process deployments without changing production storage.
