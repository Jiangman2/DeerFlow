# v2.1.0 批次 20：企业确认/执行流竞态的取消清理

## 为什么先于引用释放

对照 #5112 `45adb8fbb5a9d21a93cec160231835d58f432ab7` 的 deterministic stream close 与正式 v2.1.0 终态生命周期时，发现企业特有的 `_stream_once` 包装在 `asyncio.wait(stream_task, clarification_event_task)` 被父 task 取消后，只停止 event task。实际 stream task 可能仍在执行，而外层已释放沙箱租约。只同步 `aclose` 或清理 Journal 引用无法修复这层所有权断裂。

这是本地代码审计与合成测试发现，不是对生产故障原因作新的无证据断言。

## 实现

- finally 对本次创建的两个 task 统一 cancel + drain，不影响其他 run 的 task。
- 已收到取消的 stream 不重复 cancel，以免打断 async generator 的 finally。
- shield drain，重复 host cancellation 延迟到子任务收尾完成后再传回 worker 的取消/失权路径。
- 人工确认仍保留原先 1 秒正常收尾机会及 `awaiting_human_input` 结果；真实流异常仍是 error，不因 `gather(return_exceptions=True)` 被转成 success。
- 继续使用现有 enterprise lease / trace / WeKnora / rollback 边界；没有启用新后端或重建 Agent。

这里等待的是合作式异步清理，不能强行终止拒不退出的外部工具，也不声称能回滚已经提交的远端副作用。对不合作工具的超时、进程组停止仍由其 owning transport 管理。

## 验证

先添加单/多 stream 模式 × 主动取消/ownership loss × 一次/重复取消的 8 项 TDD，全部复现失败：parent 已收尾，child 没有开始退出。修复后全部通过。另补人工确认 timeout 的收尾顺序和真实 stream error 不被隐藏，总计 10 项新用例。

最终扩大测试：**674 通过、无跳过、1 条 Starlette/httpx 弃用警告，41.17 秒**；为上一批 661 项 + 本批 10 项 + 现有 stream_cleanup 3 项，不与之前结果相加。包含同一纯本机 PostgreSQL、各事件存储、lease/cancel/rollback/人工等待、PPT 独立执行、sandbox lease、token/owner/recovery 回归。Ruff check/format 和 scoped diff check 通过。

下一批仍需官方 #5112 的 worker-owned config/runtime callback 引用释放、延迟 terminal RunRecord 清理及对应保护测试；之后继续 changed-output 与企业 PPT/媒体真实发布边界的交付验收、扩展 stop fan-out、事件删除 fence 等依赖。完整 v2.1 对齐、离线镜像、ARM64/NFS/SSO/浏览器/存量数据回退还未验收。没有连接生产或执行发布，暂停热更继续有效。
