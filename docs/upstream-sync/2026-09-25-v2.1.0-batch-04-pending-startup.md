## 修改

1. `RunStore.start_run` 原子地将 pending 改为 running；Memory 和 SQL 均拒绝重复启动、已结束和不存在的 run。SQL 使用带状态条件的单条 UPDATE，不采用先查再无条件写。
2. `RunManager.try_start` 用每个运行的启动锁协调本进程并发启动、取消和持久化失败；持久化写入期间收到取消也不能复活任务。无法判定持久化结果则失败关闭。
3. Gateway 在 durable admission 后、下一次 await 前就挂上 worker。非关键线程元数据准备移入已挂接任务，最多等待 5 秒，取消/超时后消费后台结果，避免 pending 记录没有可取消 worker。
4. Worker 在构造 Agent、访问 checkpoint 和标记线程运行之前经过启动屏障。取消于启动前仍关闭流并执行完成回调，但不运行 Agent，不为未启动的运行写入标题/耗时或覆盖线程状态。
5. 保留企业员工/知识授权检查、渠道身份、目标线程锁与现有取消/回退语义。SQL 事务中不等待元数据或网络；不新增数据库字段，不顺带移植上游其他迁移。

## 连续复核补充：Pending 被替换

在批次 05/06 依赖检查期间，另用真实 worker 复现到 interrupt/rollback 替换 pending run 时，直接 task.cancel 会在元数据等待阶段提前退出，跳过 worker 的流结束和 finalizing 清理。该分支在官方最终标签中仍是直接取消；这是本地元数据挂接适配必须补齐的边界，不宣称是官方已经修复的行为。

增加 2 个回归用例，修改前均因 CancelledError 失败；现在与普通 cancel 入口保持一致：pending 只设置 abort 信号，running 才取消协程。旧 worker 必须真实发布 end、清理 finalizing、不构建 Agent、不覆盖线程状态；替代运行保持 pending，不能被旧清理状态堵住。
