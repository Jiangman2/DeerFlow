范围与结论
调查用户提供的 gateway-7469f8d95d-qdljj/gateway 在北京时间
2026-10-29 09:25:48 的 web_search 异常。仅分析日志、当前源码、部署声明和历史现场回执；
没有更改应用代码、生产配置、证书或部署，没有调用实际搜索 API。

已确认的直接原因：Gateway 向 api.tavily.com:443 发起 /search 请求时，
TLS 校验无法把对端证书连接到本次客户端信任的签发者，报
CERTIFICATE_VERIFY_FAILED / unable to get local issuer certificate。
本次失败发生在取得 HTTP 业务响应之前；日志不支持归因为 API Key、搜索参数或额度。

底层诱因尚未唯一确认。优先核查 local-pvc 清空 CA 配置后，信任库与实际
网络返回证书链是否匹配，同时核查新 Pod 的环境变量和运行源码是否发生漂移。
不能仅凭这段日志认定企业代理替换了证书，也不能认定 Tavily 服务端缺少某张证书。

调用路径与对象关系
web_search_tool -> _get_tavily_client -> TavilyClient.search
 -> requests.Session.post -> urllib3 -> TLS 证书链校验 -> SSLError
 -> ToolErrorHandlingMiddleware 记录异常并转换成工具错误消息。

每次工具调用创建 TavilyClient；兼容模式下持有专用 requests.Session，
Session 的 HTTPS Adapter 持有 SSLContext，并将其传给直接池和代理池。
环境 CA 文件 -> SSLContext 信任库；环境代理 -> Session 实际出站路径。
因此，“挂载了 CA”和“本次返回证书能被该 CA 验证”是两个需要分别核查的事实。

建议的下一步（只读取证）
1. 在故障 Pod 与一正常 Pod 对比镜像摘要、Tavily 源码摘要、实际 TLS 开关、
   三个 CA 路径、挂载内容摘要和 CA 集合；代理信息只输出脱敏地址与是否配置。
2. 使用相同应用 TLS 上下文和实际代理，小批量、有超时地进行握手采样，
   同时记录节点、UTC 时间、验证错误码、证书链主题/签发者/指纹。
   不发送 Tavily Key，不执行搜索，不关闭证书验证。
3. 若 CA 不一致，修复受影响副本的正确挂载/配置；若 CA 相同但返回链不同，
   关联出口代理后端及中间证书配置；若稳定缺少某个签发者，核实 CA 来源后修复完整信任链。
4. 改善诊断应优先记录脱敏的 CA 摘要、客户端配置及底层 verify_code，
   而不是增加无差别重试。Max retries exceeded 文本本身不能证明实际进行了多次重试。
